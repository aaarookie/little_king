# 《小小国王》Sprint 5 项目评审与方向建议

> **最新排期覆盖（2026-09-06）**：Sprint 6 已删除，音效/表现素材及打包/硬件测试后置；直接推进 [17 地牢规划](17-DungeonDevelopmentPlan.md)。补牌改为始终满手的 FIFO 队列，当前生效规则见 01；下文原始里程碑建议只保留历史来源。

> **后续采纳记录**：这是修订前的原始评审，保留问题证据。P0/P1 已进入本轮 Sprint 5 改动，实施与验证见 [15](15-Sprint5ChangeLog.md)。用户明确采用全单位头顶条、仅火球释放小震、嘲讽最高优先级、唯一手牌、三英雄营地和可增删特性；这些覆盖下文不同方向的建议。两英雄部署、调整开局银币、游侠新特性等实验建议未擅自落地。


评审日期：2026-09-06。状态：**建议稿，未替代 GDD，也未表示以下修复已完成。**

依据：README、docs/01~13、当前工作区 C++ 与配置，以及两张已有原图（盾卫战斗精灵、骑士立绘）。以用户说明为准：Sprint 5 代码已经完成，正在联调。当前工作区已有未提交的 Sprint 5 修改，评审针对这些修改后的代码。

本次没有运行 UE 编辑器、编译、打包或实际对战，也没有导出 `.uasset` 中的数据表数值、材质和蓝图连线。下文区分静态代码事实、条件性推导与设计建议；C++ 默认值不等于 DA_GameData 的实际覆盖值。

**我的主要判断**

当前已经具备可继续迭代的战斗基础。最值得改变的是产品优先级：先证明玩家能识别危险、有效救援英雄，并愿意再试一种构筑，然后扩充地牢与家园。

我建议将定位收紧为：**你作为国王，带领少量英雄完成短途远征，用有限的银币、援军与敕令，在自动战斗中救下关键人物并完成反击。**

保留 UE、C++、Paper2D、现有 GAS 属性/效果管线、卡牌经济与战斗阶段机。先做局部修正；当前没有足够证据支持换引擎或全量重写。家园经营、多种族扩编、大规模动画制作后移。

**一、核心承诺需要更可靠的玩家行动来支撑**

GDD 把“保英雄”列为核心策略，但当前实现存在以下组合：

- 英雄沿用自动追敌逻辑，没有战斗中的驻守或撤回指令。
- `ALKUnitBase::AcquireTarget` 中，强制集火优先于嘲讽；普通嘲讽查询半径固定为 4000，缺少独立的局部作用范围。
- 移动分离显式跳过建筑，移动代码也没有实现建筑绕行或硬阻挡。文档所说的“用建筑挡路”没有得到当前 C++ 路径的可靠支持。
- 集火目标选取血量比例最低的玩家英雄，信息主要通过日志和调试线传达。
- 法师死亡同时损失战力与法术使用权，可能继续削弱玩家救援其他英雄的能力。

这一组合容易产生“看到了危险，却缺少有效回应”的体验。是否已经频繁发生需要实测，但规则冲突足以成为 Sprint 5 的首要验证项。

建议先试一个最小方案：从现有 3 名英雄中选 2 名出征，英雄有固定驻守点和追击半径；只新增一种可控行为——**集结敕令**，选择英雄后指定新的驻守点，英雄移动到位再恢复自动作战。初版用冷却限制，不新增第二套货币。不要同时加入完整 RTS 的框选、编队和大量快捷指令。

敌方集火提前约 2~3 秒显示目标头像与标记；集火是目标偏好，允许局部嘲讽或护卫机制介入。若某种精英能突破保护，要把它做成可识别的特殊能力。建筑先明确为固定火力/保护据点；真正的挡路机制需要单独设计移动与绕行，不能靠说明文字替代。

需要验证的关键片段是：玩家看见法师即将被集火，决定保留银币、放下盾卫并撤回法师，代价是暂时失去前线输出。玩家能说清“我用什么代价救了谁”，这才是核心玩法成立的证据。

**二、建议取消当前法术硬门槛，改成英雄对构筑的强化**

当前代码只限制施放，不限制抽入手牌：`ULKDeckState` 不检查法师；开局初始化牌库也早于玩家完成英雄部署。法师死亡时广播刷新 UI，没有移除、转换或替换锁定法术。

因此当前行为与 GDD 的“法术才可加入手牌”不一致。默认兜底牌库只有 1 张法术，不能据此声称现在必然四槽锁死；但随着法术牌数量增加，持续占用多个槽位、甚至没有可出牌的情况是明确的规则风险。同类建筑达上限、单位总数达上限也会造成暂时不可用的手牌，需要一起考虑。

我的首选：**基础法术始终可用，法师存活提供施法强化或特殊联动。** 法师阵亡损失构筑优势，玩家仍有救援行动。骑士、游侠也分别强化护卫、远程等玩法，让英雄选择决定打法。

若坚持硬门槛，则必须定义完整生命周期：未带法师时的战斗牌库过滤、法师阵亡后的手牌替换与后续抽牌排除、复活例外的恢复方式，以及无可用牌时的行为。过滤只作用于本场战斗，不应直接删除远征中拥有的卡牌。

**三、经济节奏应围绕决策机会重新验证**

源码默认银币从 0 开始，每秒产出 1/3，上限 5；Sprint 2 的卡费建议为 2~5。仅按这些值计算：

| 费用 | 从零攒到可支付的时间 |
|---|---|
| 2 | 6 秒 |
| 3 | 9 秒 |
| 4 | 12 秒 |
| 5 | 15 秒 |

这些是公式推导，未核验资产中的当前费用。应检查玩家开战后是否只能等待、一次高费出牌后是否失去整个危险窗口的应对能力，以及满费滞留是策略选择还是手牌无解。

建议先只改一个变量：给开局一笔足够支付一张基础援军牌的银币，与当前零银币开局做对照。随后再单独比较恢复速度，不同时调整血量、费用、收入和波次。

对短远征，我建议普通战斗以 90~150 秒为初始实验目标，精英/Boss 可以更长。这是建议目标，不是已测出的最佳节奏。GDD 的 10~15 个房间若包含大量 3~5 分钟战斗，会迅速放大一趟远征的时间成本；应按实际战斗房数量计算总时长。

8 分钟也不是当前代码的硬上限：按默认虚弱参数，不考虑治疗、其他伤害和帧误差，第 n 次虚弱累计造成的最大生命比例为 `0.01n + 0.0001n(n+1)`，第 62 次才超过 100%。满血英雄仅靠虚弱死亡约需额外 310 秒，总计约 13 分 10 秒。短战斗应有较早且可解释的终局压力，避免把长时间等待交给虚弱机制处理。

**四、让敌方成为可读的关卡对手**

现有 AI 同时有银币出牌和不花银币的脚本波次。单机 PvE 可以采用这种不对称设计，但需要把额外援军作为明确的关卡规则，并纳入统一的遭遇强度预算。

建议优先制作 3 种可读的遭遇：盾阵推进、远程齐射、精英猎杀。每种遭遇呈现一个清楚的威胁、一个应对窗口和至少一种已有卡牌可完成的解法。先用现有兵种组合完成，不急着制作 3 个新佣兵。

当前几个 AI 细节会妨碍设计验证：

- 选牌得分是 `100 - Cost*10 + CounterBonus`，反制加分为 3。2 费普通牌得分 80，3 费反制牌得分 73；反制只能改变部分同费选择，无法抵消一银币差价。
- 所有法术共用敌方聚集点逻辑。对敌方 AI 而言，这会把治疗波指向玩家单位附近，无法可靠选中需要治疗的己方单位。
- 常规模式会不断花钱，没有明确的储备阶段；“银币足够才爆发”不等于“会主动攒钱爆发”。
- 最优候选出牌失败就返回，没有尝试次优候选。建筑封顶等情形可能让 AI 反复尝试同一张不可打的牌。

应先筛合法候选，再按伤害、治疗、护卫等实际用途选目标，最后评估是否值得花费。复杂度增加应服务于玩家可理解的行为。

**六、架构调整应跟着下一项真实需求发生**

现有 GameMode 为 1136 行，承担流程、卡牌执行、生成、AI 查询、音效、弹道池和 UI 创建。需要减轻职责，但当前体量不需要建一套通用游戏框架。

先拆两处：稳定碰撞与视觉的层级；统一战斗事件及其统计/表现订阅。进入跨房间远征时，再建立独立的远征状态，保存英雄状态、卡牌实例、随机种子和当前节点；单场 GameMode 只负责消费入场信息、产出战斗结果。

牌库预留接口需要重新审视：`RemoveCardFromDeck(CardId)` 会删除全部同名副本，`TransformCard(OldId, NewId)` 会转换全部同名副本。当前仅用 FName 标识卡牌，不能表达“只升级三张剑士中的一张”。地牢的拥有卡牌应至少区分卡牌实例 ID、定义 ID 与升级状态；战斗抽牌堆引用这些实例。预留了函数名称，并不代表跨房间构筑已经具备正确语义。

继续使用 GAS 的现有部分。等多技能独立冷却、状态叠加等实际需求出现，再补相应能力；不为了技术完整性一次迁移全部法术。文档可以直接写明目前是“GAS 属性/效果 + 英雄 GA + C++ 法术/冷却/特性规则”的混合实现。

性能方面，配置仍启用了高规格渲染相关选项，包括 RayTracing、动态 GI 和虚拟阴影。先选定一台目标机器和打包配置，在代表性密集战斗中记录 CPU/GPU 帧时间、首次出牌/音效卡顿及内存。逐项比较渲染选项、同步加载与对象数量，不能仅凭配置或存在对象池就断定瓶颈。

复现也应提前：洗牌、AI、部署和震屏都在使用全局随机函数。战斗随机与表现随机分开，记录种子、配置快照和玩家操作。固定种子有助于复现，仍需控制调用顺序与模拟时间步，不能承诺跨帧率完全确定。

**七、美术优先级调整为“先看清局势”**

已查看的盾卫精灵轮廓明确，骑士立绘适合承担角色气质；它们足以继续验证玩法。盾卫原图边缘可见绿边，后续做去色污染和透明边缘清理即可，不需要因此全量重画。最终小尺寸效果尚需战场截图检验。

建议表现投入顺序：逐英雄状态与集火预警 → 合法放置/法术范围预览 → 关键技能命中反馈与音效 → 阵营辨识 → 普通伤害飘字 → 装饰和逐帧动画。普通单位每次受击的数字和震动应减少，避免淹没英雄危险信息。

美术方向保留暖童话色板；精细装饰集中在立绘与固定界面，战场单位和地面中心优先可读性。不要把 P0 扩张成完整 UI 九件套、所有角色动画和多个敌方种族的生产任务。

相机规范应先统一：03 与原生 C++ 仍按正俯视和平铺精灵处理，07 提出改斜视建议，12 已把斜视写成现状。未检查地图资产前不能宣布斜视改造已完成。若试斜视，先验证精灵朝向、遮挡排序、鼠标与地面求交、技能圈投影和 HUD 定位；当前鼠标函数的“射线远处一点”兜底也需要改成明确的战斗平面求交或失败返回。

**八、建议替换后续里程碑的验收方法**

| 验证后扩充 | 有不同打法的内容组 | 护卫反击、远程掩护、法术控制等至少两种方向改变实际决策；再决定扩建家园、更多房间与资产 |

短远征先用简单节点界面和现有场景复用，不做可漫游家园。明确本次远征中的死亡/负伤规则；首版可以采用“本次远征退出、下次远征恢复可选”，先测玩家对损失的反应，再考虑更重的永久惩罚。战斗银币和远征奖励资源分别命名、存储和重置，避免经济混用。

奖励应提供行为差异，例如“盾卫进入护卫状态后吸引附近攻击”“治疗后的下一次攻击附加效果”，数值加成用作辅助。具体效果仍要受事件结构和现有机制能力约束，不一次增加一整套天赋树。

原先“连打 3 局、击杀比不超过 2:1”可以检查基本可玩性，不能据此宣布平衡完成。胜负由英雄生存决定，佣兵数量、费用和免费波次不同，击杀比可能误导。高水平操作也不应该被强制调成险胜。

建议记录：首次有效出牌时间、有效出牌频率、满费滞留时间、无可用牌持续时间、首位英雄死亡时间、伤害/治疗来源、集火后的玩家行动、虚弱触发率、对局时长及重开行为。策略指标和性能指标分别采集。

可先邀请 3~5 名不了解规则的测试者作定性测试，观察他们是否能识别危险、做出回应、解释结果、主动再开一局；这不是统计显著性结论。使用一组固定遭遇与种子逐项比较变量，保留原始记录，不把几个主观好评当作玩法已被证实。
